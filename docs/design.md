# Wayvia 途序网络分流设计方案

讨论稿 v3 · 更新于 2026 年 10 月 11 日

当前阶段为产品与架构设计。本文确定流量路径、组件职责和后续验收要求；部署、客户端适配与实际网络效果尚待验证。

## 1 已确定的产品目标

Wayvia 途序为独立的智能分流代理服务，使用自有阿里云服务器作为接入入口，使用自有日本服务器同时运行代理服务端和 OpenVPN 服务端。参考 Infinimesh Air 的 OpenVPN over proxy 思路，独立设计接入、路由、配置分发与运维。

**国内流量直连，国外流量经阿里云接入后从日本出口访问。** 分流发生在终端或寝室网关，国内流量无需先到阿里云。这里的国内包括校内资源及国内公网服务；默认分类拟采用中国大陆域名与 IP 规则集，特殊目标由明确规则校正。

手机需要覆盖 Android 和 iPhone，并能在 Wi-Fi 与蜂窝网络上接入。连接校园网 Wi-Fi 时，国内流量通过校园网直连；使用蜂窝网络时，通过移动运营商直连并正常消耗套餐流量。寝室路由器作为后续扩展，为未安装客户端的设备提供相同分流。

阿里云入口按中国大陆地域规划，现有实例地域仍需核实。两台服务器采用受支持的 Linux 系统，具体发行版与版本在实施前确认。OpenWrt 用于可选寝室网关。

## 2 总体架构

```text
手机 / 电脑 / 寝室路由器
    │
    ├─ 国内流量、校内和局域网资源
    │       → 当前网络直连 → 国内或本地目标
    │
    └─ 国外流量及未分类流量
            ↓ 通过当前 Wi-Fi 或蜂窝网络
      阿里云服务器
        代理接入服务
            ↓ 将业务连接交给 VPN 出口
        OpenVPN 客户端 / TUN
            ↓ 已封装的 VPN 连接
        v2rayA / 代理核心
            │
            │ 代理连接承载 VPN 连接
            ↓
      日本服务器
        代理服务端
            ↓ 在本机转交指定 VPN 端点
        OpenVPN 服务端
            ↓ 出口转发与 NAT
        日本公网出口 → 目标服务
```

物理路径为“终端 → 阿里云 → 日本 → 目标服务”。在阿里云内部，业务先进入 OpenVPN 隧道，再由代理核心承载 OpenVPN 的底层连接；日本端按相反顺序解开封装。

国内目标看到终端当前网络的出口地址。经过代理链路的目标看到日本服务器实际使用的公网出口地址。日本上的代理与 VPN 共用一台服务器，两层协议各有职责，但共享该服务器的带宽和故障风险。

回程按相反路径返回终端。阿里云必须保留客户端接入连接的正确回包路径，不能让发往客户端的回包再次进入日本出口。

## 3 组件与职责

| 位置 | 组件 | 职责 |
| --- | --- | --- |
| Android 和 iPhone | 支持所选协议的客户端 | 接管应用连接，执行分流与 DNS 策略，连接阿里云 |
| 电脑 | 兼容代理客户端 | 复用入口与规则意图，按平台提供配置 |
| 阿里云 | 代理接入服务 | 认证设备，终止终端接入连接，将业务出站交给 VPN |
| 阿里云 | OpenVPN 客户端 | 将业务流量封装进通往日本的 VPN 隧道 |
| 阿里云 | v2rayA 与配套代理核心 | 连接日本代理节点，承载 OpenVPN 底层连接 |
| 日本 | 代理服务端 | 接收阿里云的代理连接，转交本机指定 VPN 端点 |
| 日本 | OpenVPN 服务端 | 验证 VPN 客户端，解封装并通过日本公网出口转发 |
| 寝室网关 | 受支持的 OpenWrt 设备与兼容客户端 | 为指定设备执行透明代理和分流 |
| 配置分发 | 私人 HTTPS 订阅或配置文件 | 分发入口、凭据、规则与 DNS 设置 |

v2rayA 用于管理代理核心和出站节点。面向手机的接入服务需要独立配置和维护，不能把 v2rayA 管理界面作为手机节点入口。[v2rayA 官方说明](https://github.com/v2rayA/v2rayA)

阿里云接入服务和日本代理服务端可使用 sing-box 等兼容实现。具体核心、版本和协议组合需要完成兼容性验证后确定。OpenVPN 服务端需要配置 IP 转发以及出口 NAT 或对应路由，才能让隧道业务访问互联网。[OpenVPN 出口路由说明](https://openvpn.net/community-docs/routing-all-client-traffic--including-web-traffic--through-the-vpn.html)

## 4 双层链路的实施边界

### 日本代理与 VPN 的本机衔接

日本代理服务端和 OpenVPN 服务端使用独立监听端点。VPN 端点可监听本机或受限内部接口；代理服务端仅允许转交到指定 VPN 地址、端口和传输协议。

实现时必须区分“日本代理的公网端点”和“由代理转送的 VPN 端点”。阿里云代理核心可以通过物理网络连接日本代理；OpenVPN 的底层连接必须进入代理路径。这样可以避免直连例外放宽后，使 OpenVPN 意外绕过代理。

TCP 或 UDP 的选择须与整条代理链路匹配，分别验证握手、数据转发、重连及 MTU。OpenVPN 支持经代理传输，但具体组合以所选核心与服务端的实测结果为准。[OpenVPN 手册](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html)

### 阿里云接入与出站隔离

建议采用独立网络命名空间或等价的进程与路由隔离，将接入后的业务出站导入 OpenVPN。客户端接入连接的回包、SSH 管理及明确列出的基础设施通信保留各自的正常路径。

部署时需要分别识别三类连接：

- 终端到阿里云的接入连接，回包沿入口连接返回。
- OpenVPN 到日本 VPN 端点的底层连接，只能通过代理核心发送。
- 代理核心到日本代理公网端点的连接，从阿里云物理网络发出。

不得直接把 Air 的主机全局规则搬到公网接入网关。网关需要额外处理入站、回程、转发和服务隔离。

### 双层各自提供的能力

代理层提供阿里云与日本之间的传输通道；VPN 层提供统一的虚拟网络出口、证书认证和路由边界。手机仅连接阿里云入口，VPN 证书由阿里云与日本两端使用。

两层同机部署无需引入额外代理供应商。双层封装会增加处理和报文开销，性能需要通过实际业务测试确定。

## 5 客户端接入与配置分发

终端接入与服务器之间的代理承载是两个独立协议选择。首版终端接入保留 Trojan over TLS 作为候选，开启证书校验；mihomo 与 sing-box 均有相应配置支持。最终选择以 Android、iPhone 和网关所用客户端的实际兼容性为准。[mihomo Trojan 配置](https://wiki.metacubex.one/config/proxies/trojan/) · [sing-box Trojan 入站](https://sing-box.sagernet.org/configuration/inbound/trojan/)

客户端交付内容分为三部分：

| 内容 | 用途 |
| --- | --- |
| 阿里云节点信息 | 建立接入连接，包括地址、端口、协议、认证与证书参数 |
| 完整客户端配置 | 同时携带节点、国内直连规则、默认代理策略和 DNS 设置 |
| 私人订阅地址 | 后续更新配置和规则，并支持撤销或轮换访问凭据 |

单个节点分享链接不等于完整分流配置。Android 拟优先适配选定的 mihomo 兼容客户端；iPhone 按选定客户端生成其支持的格式。两端共用配置来源与规则意图，配置文件按平台适配。

手机需启用客户端的系统 VPN 或 TUN 接管模式。代理支持的应用和协议范围须逐项验收，包括 UDP；仅设置浏览器或 Wi-Fi HTTP 代理不足以覆盖全设备需求。[mihomo TUN 说明](https://wiki.metacubex.one/config/inbound/tun/)

终端只获得连接阿里云所需的凭据。阿里云到日本的代理凭据与 OpenVPN 私钥保留在服务器侧。首版先支持配置文件导入，验证后增加私人 HTTPS 订阅；复杂管理面板不作为首版前提。

## 6 分流与 DNS 策略

### 终端和网关的规则顺序

| 顺序 | 匹配对象 | 行为 |
| --- | --- | --- |
| 1 | 阿里云入口的底层连接 | 经当前物理网络连接，避免循环代理 |
| 2 | 局域网、网络认证入口、校内域名与实际网段 | 直连 |
| 3 | 明确维护的国内目标及国内域名规则集 | 直连 |
| 4 | 国内 IPv4 和 IPv6 地址规则集 | 直连 |
| 5 | 国外目标及未分类目标 | 进入阿里云，最终从日本出口访问 |

默认规则保持“国内直连”。规则更新或误分类修正需要保留这一原则。域名、IP 归属和 CDN 部署并非总是一致，应记录规则版本及误分类案例，并通过明确规则修正。

校内资源可能使用公网地址，因此需要维护实际域名与网段，不能只依靠私有地址识别。离校后，直连规则本身不会赋予校内资源的访问权限。

### DNS 与路由保持一致

- 校内域名使用当前可达的校园 DNS 或指定内部解析器。
- 国内域名使用直连侧解析路径，避免全部查询绕行日本。
- 国外域名通过代理路径解析；服务器侧相应查询随业务进入日本 VPN 出口。
- 阿里云入口与日本代理节点的启动解析有独立路径，避免“尚未连上代理却依赖代理解析”的循环。

客户端需配合域名规则和 IP 回退规则处理未知目标。系统私人 DNS、浏览器加密 DNS、应用自带解析和缓存均纳入验收；不能仅检查系统 DNS 设置就认定路径正确。[mihomo DNS 配置](https://wiki.metacubex.one/config/dns/)

### IPv6 与故障行为

IPv4 和 IPv6 同时纳入规则。若首版代理链路未支持 IPv6，需要阻止应代理的 IPv6 流量意外直连，并验证应用能否使用 IPv4；国内直连的 IPv6 按规则正常处理。

在客户端运行且接管对应流量时，代理链路故障应使代理请求失败，国内与校内直连继续工作。阿里云不得在 VPN 或代理故障后，把对应业务自动改为物理直出。

用户主动停止客户端后的行为取决于操作系统设置；首版不承诺跨所有客户端实现系统级持续阻断。服务器网络配置变更需要保留可用管理路径及失败回退；正常运行中的出口故障则保持业务阻断，两类行为分别验证。

## 7 寝室路由器与移动使用

手机方案先独立运行，使用蜂窝网络时也连接同一个阿里云入口。切换 Wi-Fi 与蜂窝网络时通常需要重连，现有通话、下载或长连接可能中断，恢复时间通过实测记录。

网关扩展使用受支持的 OpenWrt 设备。对没有客户端的设备，网关负责国内直连和国外代理。对已经启用客户端的手机，网关放行它到阿里云入口的连接，避免重复套入代理。

路由器型号、CPU、内存、固件支持及校园网认证方式在接入前核实。服务器采用常规 Linux，OpenWrt 作为接入网关的可选平台。

## 8 凭据与运行信息

终端凭据按设备或用户分别签发，支持撤销与轮换。订阅链接按访问凭据管理，使用 HTTPS；OpenVPN 使用受信任的证书并校验服务端身份。

管理界面仅通过受限管理路径访问。日本代理服务端的转发目标限制在 VPN 端点，服务器之间的服务认证与终端接入认证分别维护。

日志拟保留连接阶段、错误类型、延迟、流量计数和组件状态，避免记录密码、私钥、订阅令牌及业务正文。代理运营端仍可能接触目标地址等连接元数据；终端至阿里云、阿里云至日本分别形成加密连接，应用 HTTPS 的端到端证书校验保持开启。

## 9 实施顺序

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 1 部署输入确认 | 确认阿里云地域、两端系统、资源与带宽，选定客户端和候选协议 | 明确组件版本、配置字段及测试应用 |
| 2 服务器链路 | 在日本部署代理与 VPN，在阿里云建立 OpenVPN over proxy | 受控测试流量使用日本出口，底层连接路径正确 |
| 3 终端接入 | 增加阿里云接入服务，生成 Android 和 iPhone 配置 | 在可用测试网络验证国内直连与国外代理 |
| 4 完整功能验收 | 测试 DNS、IPv6、UDP、故障、凭据撤销与网络切换 | 达到下节标准，记录性能与费用 |
| 5 实际环境适配 | 在目标 Wi-Fi 环境验证入口连通性，按证据定位问题 | 记录实际可用范围和未解决项 |
| 6 网关扩展 | 接入符合条件的 OpenWrt 设备 | 无客户端设备可用，已有客户端不发生重复代理 |

当前继续完成方案讨论。部署和编码留待进入实施阶段后开展。

已有环境现象是：启用 Clash 后校园网下节点超时，关闭后立即恢复，相同节点在蜂窝网络可用。该现象作为后续实网适配输入，尚不能确定为 DPI 或账号封禁。本轮先确定产品与服务器链路，校园网检测和故障专项排查按用户安排后置。

## 10 验收标准

| 项目 | 通过条件 |
| --- | --- |
| 国内与校内访问 | 在目标设备上命中国内规则，出口为当前网络；两台服务器无对应业务转发 |
| 国外访问 | 终端接入阿里云，目标看到日本出口；不从终端直接连接日本 |
| 双层顺序 | 阿里云 OpenVPN 底层连接由代理承载，日本代理仅转交指定 VPN 端点 |
| 回程与管理 | 业务响应可回到终端，管理连接与接入回包没有错误绕行 |
| DNS | 校内、国内、国外与启动解析分别符合策略，代理查询没有意外走直连 DNS |
| IPv6 | 直连与代理规则一致；不支持的代理 IPv6 按设计阻断 |
| TCP 与 UDP | 所选组合通过网页、下载、实时通信等实际应用测试 |
| 链路中断 | 分别停止代理与 VPN，代理业务失败，国内与校内直连仍可用 |
| 重连与变更 | 重启后恢复规则；错误配置可回退；不会形成循环代理 |
| 认证与订阅 | 无凭据不能使用服务，撤销凭据后按约定时限失效 |
| 多端与网络切换 | Android 和 iPhone 分别完成导入、更新、连接与切网测试 |
| 网关扩展 | 指定设备按规则分流，手机客户端连接没有重复代理 |

链路健康检查分别覆盖代理端点握手、VPN 建立和最终业务请求。日本代理只允许 VPN 目标时，不使用“经该代理访问任意网站”作为代理层健康检查。

记录入口连接时间、目标请求时间、吞吐量、丢包及重连时间，并与同一时段的基线比较。速度目标和 SLA 在取得实际测量后确定。

## 11 成本与待确认输入

国外业务经过阿里云和日本，两端的带宽上限、计费方向、流量额度及双层封装开销都会影响成本和体验。国内直连业务不消耗这两台服务器的业务转发带宽。系统吞吐量受路径中最慢的一段及服务器处理能力限制。

实施前仍需确认：

- 阿里云现有实例的地域、操作系统、CPU、内存、带宽与流量计费方式。
- 日本服务器的系统、资源、出口带宽、可用公网地址及现有服务占用。
- Android 与 iPhone 的具体客户端及版本。
- 接入域名与证书条件，两段代理协议与 OpenVPN TCP 或 UDP 组合。
- 校内域名与网段、国内规则来源、DNS 解析器、主要应用及 UDP 需求。
- 预期用户数、并发设备数和可接受的带宽费用。
- 寝室路由器型号与固件支持，作为后续网关扩展输入。

## 12 对外定位

产品品牌为“Wayvia 途序”，对外定位为“智能分流代理网关”，介绍代理接入、国内直连、多端配置和自有海外出口。技术架构保留真实的代理与 VPN 分工，实施状态在设计与验收资料中维护。
