# Windows / i-hdu 正常路径诊断

日期目录按开发机 2026-10-20；实测主要窗口为 UTC 2026-10-21 03:49–04:03（北京时间 11:49–12:03）。只读检查用户授权的 Windows 客户端和既有两台服务器，不修改客户端配置、路由、防火墙或服务，不做故障注入、主动重启和吞吐压测。用户在测试中自行开启 TUN，并明确确认。

## 结论与边界

国内直连、国外 IPv4 经 Wayvia 的选定正常路径已验证；不能宣称全设备、全部协议或长期稳定性验收通过。国外 IPv6 拒绝符合当前设计，不是新增的 IPv6 支持故障；但默认地址选择的 curl 请求选择 IPv6 后没有回退 IPv4，形成可复现的客户端兼容问题。另捕获两次独立的服务器自然降级，不能全部解释为用户切换 TUN，更没有证据直接归因于校园网拦截。

实际版本为 Clash Verge **1.7.2** / Mihomo **1.19.31** / Windows 11 Home build 26200。此前用户指定 **1.19.13** 的结果仅为容器内订阅解析校验，不能混作当前实际核心。规则模式、Wayvia-entry 选中、系统 HTTP 代理开启。服务模式核心启动于 03:51:02.793 UTC；此后 TUN 开启，规则保持一致。此前国内/国外 HTTP 代理分流证据与此后的 TUN 证据分开保存。

## 分流与可达性

- TUN 前：百度、腾讯 API 连接记录命中 `DIRECT`，Google、Wikipedia 命中 `Wayvia-entry / Wayvia`。腾讯 robots 路径返回 501，仅证明 TLS/HTTP 到达，不算页面成功。
- TUN 后：百度 IPv4 三次 HTTP 200，日志命中 `DomainSuffix(baidu.com) → DIRECT`；Google IPv4 三次 204，日志命中 `Match → Wayvia`。YouTube 三次 204，GitHub robots 三次 200。测试端点不代表视频播放或完整网页性能。
- Cloudflare trace：无显式 HTTP 代理的 TUN 请求三次 200，API 记录类型 `Tun`、链路 Wayvia，回显出口三次均匹配日本服务器；显式 HTTP 代理对照三次也匹配日本。证书验证保持开启。
- 04:03 的核心 TCP 快照在明确筛选的阿里云入口、日本公网及 CF 测试 IP 中，仅发现到阿里云入口 8443 的连接；该快照不能证明电脑所有应用都只连接国内地址。
- IPv6：默认 Google 请求三次快速失败，以及强制 IPv6 三次失败，都与核心 `IPCIDR(::/0) using REJECT` 日志逐时对应。运行规则为 `IP-CIDR6,::/0,REJECT,no-resolve`；强制 IPv4 三次成功，HTTP 代理对照两次成功。这里的缺口是地址选择/IPv4 回退，不是要求放开不支持的国外 IPv6。
- WLAN 无全局 IPv6 地址；curl 在 TUN 中显示百度 IPv6 地址而成功，并不证明物理网络 IPv6 出口已验收。DNS 配置仍允许 AAAA；先前 DNS 数量探测只记录 RCODE/answer count，不足以独自证明 RR 内容或全应用 DNS 无泄漏。

## 延迟

所有网站数字为小响应、HTTP/1.1、TLS 校验开启的新连接首字节耗时，含握手与服务器处理，不能当作 ping。没有做本轮下载吞吐测试。

| 路径 | 样本 | 结果 |
| --- | --- | --- |
| 电脑 → 阿里云入口 ICMP | 5 | 中位 9 ms，范围 8–10 ms |
| 电脑 → 阿里云 8443 TCP | 5 | 中位 10.90 ms，范围 9.11–20.81 ms |
| 百度 IPv4 / DIRECT | 3 | 首字节中位 121.74 ms，范围 115.83–127.83 ms |
| Google IPv4 / Wayvia | 3 | 首字节中位 286.00 ms，范围 273.17–622.20 ms |
| YouTube IPv4 / Wayvia | 3 | 首字节中位 294.35 ms，范围 276.22–328.07 ms |
| GitHub IPv4 / Wayvia | 3 | 首字节中位 921.25 ms，范围 671.16–1088.14 ms |
| Cloudflare IPv4 / TUN | 3 | 首字节中位 256.92 ms，范围 245.97–273.91 ms |
| Cloudflare 同一 TLS 连接复用 | 4 | 首字节中位 62.62 ms，范围 60.24–67.26 ms |

最后一组首次请求为 258.62 ms，TLS 完成累计 189.64 ms；后四次 `num_connects=0`。复用消除了新连接握手成本，但并非每个网站都会得到相同延迟。复用批次中的 `at` 是收集完 curl 输出后的序列化时间，耗时来自各次 curl 自身计时。

初始 Google HTTP 代理请求还发生过一次约 5 秒超时，核心日志为入口连接 deadline exceeded，根因未确定；所有失败均保留，没有从原始结果删除。03:51:37–03:52:10 一组请求在 TUN 核心启动后执行，并与服务器异常重叠，不计入上述稳定时段中位数。

## 自然降级与延迟尖峰

只读日志窗口 03:48–03:59:48：阿里云 44 轮，42 ACTIVE / 2 DEGRADED；日本 44/44 ACTIVE。

| 阿里云 access 失败 | 进入 DEGRADED | 回到 ACTIVE | 状态降级时长 |
| --- | --- | --- | --- |
| 03:51:53.118 | 03:52:01.292 | 03:52:18.491 | 17.20 s |
| 03:58:45.132 | 03:58:55.639 | 03:59:08.588 | 12.95 s |

两次均为 `HTTP_TLS_FAILED` / curl 35，约 5 秒、HTTP 0，无已完成响应后关闭标记；区别于前次修复的成功响应被 relay 关闭异常覆盖。停止与重建来自现有 monitor 自动恢复，非本次主动操作。状态区间不是完整业务影响时长，业务失败可早于 DEGRADED 写入。

同时段承载 TCP 采样显示：阿里云侧 RTT 可达 1295 ms、1283 ms，日本侧也出现约 1.2 秒 RTT，第一次窗口的日本发送重传累计 173→438，第二次 808→945；对应 ICMP 多数约 39–47 ms。第二次在进入 DEGRADED 前，VPN 内两个 CF HTTPS 对照已达到 2 秒预算超时，DNS 对照上升至 1459/1534 ms；日本本机 DNS 与 HTTPS 对照仍成功。第一次失败前约 3 秒 VPN 对照成功，不能据 30 秒采样断言失败瞬间所有内部路径均健康。

证据支持承载 TCP 在业务负载下排队/重传的方向，不能仅用地理距离或校园网拦截解释；但尚未分清提供商整形、具体排队位置、承载 TCP 队头阻塞等贡献，不能宣称唯一根因已解决。该时段正常业务来自用户既有客户端，未采集其浏览内容，也未由本次诊断发起带宽负载。独立 24 小时观察继续运行。

## 校园网识别与拦截

已验证的代理流量在校园网一侧连接阿里云入口；阿里云→日本→目标网站发生在服务器侧。这减少了客户端直接连接境外目标的暴露，但不等于隐身：入口 IP、端口、连接时序与流量大小仍可观察，不能保证不被分类或拦截；TLS 本身也不消除流量分析，见 [RFC 8446 E.3](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-E.3)。阿里云至日本的跨境段也仍存在网络阻断风险。

用户提供网络名 i-hdu，未提供其内部识别策略。此诊断无法确认学校采用的判定规则，更不能保证今后不会被墙。TUN 前不遵循系统 HTTP 代理的程序、加密 DNS、UDP/QUIC 与全应用接管尚未完成矩阵验收；当前结果不得扩展为电脑所有通信均不暴露境外目标。
