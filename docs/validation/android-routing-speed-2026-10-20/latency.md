# LTE 延迟分段与异常恢复记录

2026-10-20 UTC，使用同一手机、CMFA 2.11.35.Meta 和现有配置。未切换网络或修改配置。完整样本、失败记录与时间线见 [latency.json](latency.json)。

## 当前请求耗时

经 USB 将请求交给手机 Clash，再由手机蜂窝网络访问同一 Cloudflare HTTPS trace 端点。每个新连接由独立 curl 进程发起；复用组由同一 curl 进程顺序请求，后五次 `num_connects=0`。全部 HTTPS 200，证书校验成功。

| 测量 | 范围 | 中位数 |
| --- | --- | --- |
| 新建连接至小响应完整返回，5 次 | 567–665 ms | 605 ms |
| 其中从开始到目标 TLS 握手完成 | 443–542 ms | 485 ms |
| 复用连接至首字节，5 次 | 77–89 ms | 86 ms |
| 复用连接至小响应完整返回 | 87–135 ms | 120 ms |

新连接的主要耗时发生在代理协商、目标连接与 TLS 建立阶段，建立后的小请求明显更快。这里的 TLS 完成时间从请求开始累计，包括之前的工作，不是单独的加密 CPU 耗时；各层内部耗时尚未完全分离。计时定义见 [curl APPCONNECT_TIME](https://curl.se/libcurl/c/CURLINFO_APPCONNECT_TIME.html) 与 [STARTTRANSFER_TIME](https://curl.se/libcurl/c/CURLINFO_STARTTRANSFER_TIME.html)。

同一 HTTPS 目标的新连接对照：日本主机直接访问中位数 65 ms；阿里云经现有业务桥接和代理/VPN 链路访问中位数 259 ms。这些请求耗时不能与下表各类 RTT 精确相加。

## 网络分段

| 测量路径 | 方法 | 结果 |
| --- | --- | --- |
| 手机蜂窝接口 → 阿里云 | 显式绑定当前 rmnet0，10 次 ICMP | 平均 51.2 ms，14.3–93.9 ms |
| 阿里云 → 日本承载端口 | 8 次 TCP 443 建连 | 平均 41.7 ms，38.7–46.8 ms |
| 阿里云 → 日本 VPN 对端 | namespace 内通过现有 VPN-over-proxy 发 8 次 ICMP | 平均 46.6 ms，39.3–65.2 ms |
| 日本 → Cloudflare 1.1.1.1 | 8 次 ICMP | 平均 3.2 ms，3.0–3.5 ms |

手机接入段在这些样本中抖动最大；跨境承载约 42 ms。通过代理承载的 VPN 对端 RTT 与直接承载建连处于相近量级，未观察到小报文在 VPN 内稳定额外等待几百毫秒。这不排除下载负载下的排队、重传或吞吐问题。

日本公网地址的 ICMP 探测没有回复，未将其当作业务丢包率，改测实际开放的 TCP 承载端口。手机 `ss` 无权取得完整 netlink TCP_INFO，回退输出中的 RTO 未当作 RTT。所有可回复 ICMP 组在此次小样本中均无丢包，不能据此宣称长期零丢包。

## 观测到一次真实异常

日志显示异常先出现，现有健康检查随后执行降级和恢复：

| UTC 时间 | 证据 |
| --- | --- |
| 09:25:10 | 阿里云业务探针开始，约 5.3 秒后失败 |
| 09:25:20 | 日本出口 HTTP 探针开始，约 12 秒后 `COMMAND_TIMEOUT` |
| 09:25:32 | 日本进入 DEGRADED，停止出口服务；现有 VPN 会话断开 |
| 09:25:36–41 | 日本恢复 VPN 与出口，返回 ACTIVE |
| 09:25:42 | 阿里云进入 DEGRADED，停止入口 |
| 09:25:43–49 | 现有恢复逻辑重启承载与 VPN，再启动入口 |
| 09:25:51 | 阿里云返回 ACTIVE |

从日本停止出口至阿里云重新 ACTIVE 约 **19 秒**，阿里云入口进程停止约 **7 秒**。最初的探针失败更早，不能把 19 秒当作本次全部故障时长。该事件可以造成秒级超时、断连和重新握手，属于稳定性问题；最初为何超时仍未确认。

这是正常诊断期间从日志观察到的自发事件，由已经部署的监控逻辑执行恢复，本轮没有主动停止服务、注入故障或重启机器。它不能替代用户要求另行安排的正式故障/重启验收。后续 HTTPS 样本均在恢复后取得。未将健康探针缺少客户端证书而产生的每条 OpenVPN 握手日志都算作业务断线。

下一步应优先追查出口探针超时来源与跨主机恢复过程，保持受保护流量 fail-closed。前一轮约 1.7 Mbps 的下载吞吐与这里约 0.1 秒的稳定连接响应是不同指标，不能把二者互换。
