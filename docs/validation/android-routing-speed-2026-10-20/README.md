# 实体 Android 分流与下载测试

2026-10-20 UTC，沿用已发布配置，在 HUAWEI HBN-AL10 / Android 12 / Clash Meta for Android 2.11.35.Meta 上测试。手机保持中国移动 LTE，VPN 持续运行，未切网、修改分流配置或变更服务器网络。

**结论：所测国内与国外目标分流正确；国内下载可用，国外代理下载偏慢。服务器侧也能复现约 1.65 Mbps，瓶颈范围已缩小至现有阿里云到日本的业务链路，具体原因尚未隔离。**

随后补测延迟：连接复用后的首字节中位数 86 ms、小响应完成 120 ms，新连接完成中位数 605 ms。同时从服务器日志发现一次探针超时及自动降级恢复，不能把此前正常路径通过等同于长期稳定。详见[延迟分段与恢复记录](latency.md)。

## 分流证据

- 手机浏览器打开国内 IP 查询，首轮看到中国移动 IPv4，后续连续五次返回手机自身已分配的移动公网 IPv6，均为 200。已将响应 IPv6 与手机接口地址逐一比对。Clash 日志记录 `myip.ipip.net` 命中国内 CIDR，使用 `DIRECT`。这是所测国内 IPv6 的直接证据，完整 IPv6 矩阵仍未验收。
- 手机浏览器打开 Cloudflare trace，连续五次均返回配置中的日本出口，`loc=JP`、`colo=NRT`；Clash 日志使用 `Wayvia[Wayvia-entry]`。
- 国内下载目标 `mirrors.tuna.tsinghua.edu.cn` 命中 `DomainSuffix(cn)` 并使用 `DIRECT`；国外下载目标 `speed.cloudflare.com` 使用 Wayvia。
- 百度 HTTPS 返回 200；Google generate_204 返回 204。腾讯在默认 curl User-Agent 下返回 501，使用 Android 浏览器 User-Agent 后返回 200，耗时 0.300 秒；未将前一次响应当作代理连通失败。

证据：[浏览器出口与响应](phone-browser-probes.json)、[目标连接日志](selected-routing.log)、[网页探针](web-probes.json)。真实出口地址与设备序列号不进入仓库记录。

## 下载结果

每次下载 2 MiB，每组 3 次，单连接顺序进行；下表速度包含连接和首字节等待，使用十进制 Mbps。正文阶段速度另存于原始指标。

| 路径与测量方式 | 三次 Mbps | 中位数 |
| --- | --- | --- |
| 手机 Clash 国内直连，USB 发起请求 | 10.662 / 17.718 / 14.235 | 14.235 |
| 手机 Clash 国外代理，USB 发起请求 | 1.148 / 1.452 / 1.360 | 1.360 |
| 手机浏览器实际国外下载 | 1.591 / 1.678 / 1.697 | 1.678 |

USB 只负责把请求交给手机本地 mixed proxy；目标连接、DNS 和分流由手机 Clash 执行，互联网流量使用手机蜂窝网络。国内样本使用镜像文件的 2 MiB Range，返回 206；国外样本使用 [Cloudflare 官方测速下载 API](https://github.com/cloudflare/speedtest)，返回 200。TLS 校验保持开启。第一组 USB 下载与少量浏览器出口探针有重叠，后两组及浏览器测速单独执行。

浏览器测试通过手机自身页面执行 fetch 并计时。国内镜像在浏览器 Range 请求下返回 403，保留为失败记录，没有把错误页大小计入网速。浏览器国外三次均完整收到 2 MiB。浏览器网络事件显示本地代理地址，因此这里只确认实际浏览器路径，不能据此替代全部应用的 TUN 验收。

浏览器复用连接的小响应请求，国内耗时 89–208 ms，国外 84–522 ms；这些是请求完成时间，不是 ICMP ping，也不用于证明长期延迟稳定。

已知成功下载的手机测试正文合计 **18 MiB**；探针、页面资源、协议头、重传及手机后台流量另计。数据文件：[USB 测量](phone-proxy-downloads.json)、[手机浏览器测量及国内 403](phone-browser-downloads.json)。

## 服务器分段对照

手机测速结束后，对同一 Cloudflare 2 MiB 目标顺序采样：

| 测试路径 | 完整请求吞吐 |
| --- | --- |
| 日本服务器直接访问 | 8.906 Mbps |
| 阿里云经现有业务桥接、OpenVPN-over-proxy 到日本，第 1 次 | 1.646 Mbps |
| 同一路径，第 2 次 | 1.661 Mbps |

服务器侧链路与手机代理速度接近，说明瓶颈能在手机接入之前复现。尚未区分云带宽套餐、跨境线路状况、TCP 重传与双层封装的各自贡献，不能把这些候选原因写成已确认根因。测试时相关服务 active，未见明显整机负载饱和；没有进行故障注入、重启或参数调整。

最初直接在业务 namespace 运行普通 curl，因该 shell 的操作系统解析路径不可用而退出 6；随后通过实际业务 SOCKS5H 桥接及其 DNS 路径完成对照，未更改解析器。失败与重试均保留在[服务器对照](server-comparison.json)。

未修改生产源码、手机分流配置或两台服务器配置；此前同一任务的四项软件门禁结果见[部署前复核](../deployment-review-2026-10-20/README.md)。本轮检查 JSON/YAML、脱敏和差异格式，临时 USB 转发在完成后移除，保留手机 VPN 运行。收尾结果见 [summary.json](summary.json)。
