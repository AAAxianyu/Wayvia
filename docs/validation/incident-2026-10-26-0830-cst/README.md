## 原因能确定到哪一步

- **已确定的软件影响：** 健康检查失败后保护动作停止入口，下一轮恢复重放全部服务动作。这与源码 `TransactionManager.monitor` / `_rebuild` 和 `LinuxExecutor.protect` 一致，也由三次实际的四项服务停启顺序证实。既有会话因此被清除，恢复策略放大了短时数据路径异常。
- **可以缩小的范围：** 出问题的是从阿里云经既有承载/VPN 访问出口的业务路径。同期入口新建 `vpn_handshake` 约 0.5 秒，VPN 会话状态 CONNECTED；日本对外 HTTP/DNS 均成功。因此没有日本服务器整体失联证据，也不能只用校园网侧问题解释服务器自身发起的失败。握手和会话状态成功不代表既有隧道吞吐正常。
- **尚未确定：** 既有承载 TCP 排队/重传、隧道数据面阻塞、跨境或日本接入侧的具体异常点。两端独立 5 秒采样已按原定任务于 10-22 结束，本事件没有同刻的双端 TCP/ICMP 记录，不能用上轮数据代替此次根因证据。生产探针没有保留足够细的连接/首字节阶段数据。
- JXY 当前账号 active、无待执行动作，最后账号变更为 10-21；所查窗口无该设备审计变更，订阅未撤销且未过期。没有账号撤销导致本次重复断连的证据。
