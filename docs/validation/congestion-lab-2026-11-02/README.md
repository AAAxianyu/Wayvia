# 共享出站拥塞隔离实验：2026-11-02

验证 [ADR 014](../../adr/014-congestion-aware-health-and-exit-shaping.md) 的出口整形、隧道公平队列、OpenVPN 重启后的自愈和宽限期 fail-closed。结构化结果：[congestion-result-256kb.json](congestion-result-256kb.json)。没有连接或改动生产服务器。

## 环境与方法

- 一次性 privileged 容器，`--network none`，标签 `org.wayvia.disposable=congestion`；镜像 `wayvia-lab:locked`，内核 6.8.0-117-generic（arm64），组件为锁定的 sing-box 1.14.3、OpenVPN 2.6.19、v2rayA/core 2.5.10。源码只读挂载。入口：`scripts/congestion_lab.py`，实验：`deploy/lab/congestion.py`。
- 复用路径实验的六个 namespace 与 ServerRenderer/ProfileRenderer 正式产物。日本只有一个上联 `jfa`（相当于生产 `ens17`），接入 `provider` 桥；provider 用 ifb 把日本发出的全部流量送入 `tbf rate 2mbit limit 256kb` FIFO，模拟云实例出站额度。因此设备下载（日本 → 阿里云隧道）与设备上传（日本 → 目标）共用一个额度，与生产一致。
- 负载：终端经 TUN 向国外目标 4 条 TCP 上传、4 条下载或两者同时，各 60 秒。上传吞吐按接收端计数（本地 TUN 会先接收远多于路径能送达的数据）。每个场景前用 `ss -K` 重置负载连接并等待路径空闲，避免中继缓冲中残留的上传影响下一场景。
- 探针每秒一次、5.75 秒期限（与生产单次尝试一致）：`egress` 从 `wayvia-egress` 经 OpenVPN 到目标；`device` 从终端经入口、承载、VPN 到目标。
- Wayvia 整形全部通过生产 `LinuxExecutor` 的 `shaping` 动作与 `ShapingSpec` 应用。

所有负载场景中，入口与出口承载套接字在每个 15 秒采样间隔内 `bytes_received` 均增加，即 ADR 014 的"承载仍在前进"信号在拥塞时稳定成立。

## 定位与探索

- 上传满载时积压在 provider FIFO（约 160 KB）；网卡整形把它移到日本本机后探针恢复。
- 下载满载时积压在日本 sing-box 承载套接字的未发送队列（无整形约 615 KB，有网卡整形约 184 KB），所有下载与探针回包同在一条承载流里排队，网卡公平队列无效。
- 30 秒探索中，`tcp_notsent_lowat` 16 KB、OpenVPN `sndbuf`/`rcvbuf` 64 KB 与 `tcp-queue-limit 16` 单独或组合均未改善下载探针（p50 4.6–5.8 秒）；只有在 tun0 上限速并用 `fq_codel`，下载探针才降到约 0.08 秒。
- tun0 速率高于承载保证份额时，上传竞争会把积压推回承载套接字（反例 p95 约 2 秒），因此 `ShapingSpec` 要求 `tunnel_kbit < carrier_kbit`。

## 自愈与安全

- OpenVPN 重启后 tun0 根队列回到 `fq_codel`；生产 `ensure_shaping()` 恢复 `htb`，再次调用为空操作。
- 宽限期：入口与终端保持运行、上传负载进行中，分别终止日本 OpenVPN 与日本代理。受保护 TCP 与原生 TCP 均失败、国内直连与管理回程正常、恢复后路径重建；期间国外目标只看到日本 NAT 地址 `10.74.0.1`，没有物理直出。

## 结论与边界

- 推荐参数满足方案的时延门槛（满载 P95 < 1.5 秒、零失败）。**吞吐门槛（≤10% 下降）未满足**：上传 −14%、下载 −19%，双向时上传只剩约 0.17 Mbit/s（隧道份额优先）。这是取额度九成与隧道限速的代价，需要用户决定是否接受或按实测额度上调。
- 未运行真实 monitor 计时器，降级与否由单元测试中的判定逻辑和此处"零探针失败、承载持续前进"共同推断。
- 实验 FIFO 大小（256 KB）与 2 Mbit 是对供应商限速器的假设；真实整形器的缓冲与突发未知。不等于生产验收。
