# 探针超时修复、延迟与带宽复核

日期：2026-10-20，记录时间统一为 UTC。分支 `codex/deployment-readiness-20261020`，源码基线 `0e5bbbc63b59031377b698311f0cb6fda44c5401` 加本工作区补丁。两台主机均为用户指定、授权部署的 Ubuntu 24.04/amd64 实例。

## 结论与边界

已在两端部署有限时备用出口探针和 OpenVPN TCP_NODELAY。出口健康检查不再绕回阿里云；入口仍需经完整业务链路验证日本出口身份。两端新事务 ACTIVE、重新显式发布，观察窗口的计数和失败情况以 [summary.json](summary.json) 为准。短时健康不能代表长期稳定验收。

最终窗口为 10:06:12 至约 10:20:52（约 14 分 40 秒），两端各 56 轮监控、各 392 项分层检查全部健康。10:16:50 阿里云入口认证探针第一次尝试出现 `HTTP_TRANSPORT_FAILED`（326 ms），备用尝试 207 ms 返回 200 且身份正确；该轮保持 ACTIVE，没有触发重建。这是真实自然发生的备用成功，并非主动故障注入；首次失败发生在传输建立阶段，不能据此认定 Cloudflare 主端点本身故障。

手机随后停止代理，用户明确确认是手动操作。这次停止不计入断连，也没有据此认定系统清理导致活动 VPN 故障；保持手机停止状态，临时 ADB 转发已清理。更细的手机 CONNECT/TLS 分段测试因此未完成。

**低带宽不能单独解释空闲时的新建请求耗时。** 本轮完整服务器链路的新建 HTTPS 中位数从约 259 ms 降至 171 ms，日本直连仍约 64 ms；手机 Wi-Fi 新连接约 493 ms、复用连接约 71 ms。当前吞吐仍约 1.6 Mbps，日本公网出站实测约 1.85 Mbps。建连等待、空闲往返和满载排队分别评估。

## 原故障证据与修复

[修复前监控事件](original-monitor-events.json)显示，09:25:10 起阿里云业务、承载身份、出口和 DNS 相继失败；日本 09:25:20 的单一出口 HTTP 探针超时约 12 秒，随后 09:25:32 进入 DEGRADED 并停止承载服务。阿里云亦进入 DEGRADED；日本约 09:25:41 恢复，阿里云约 09:25:51 恢复。日本停止至阿里云 ACTIVE 约 19 秒。

网络超时发生在服务停止之前，最初瞬时网络异常的具体来源尚未证明。可以确认的是：旧日本出口探针依赖跨境返回阿里云 HTTPS 9443，单点超时触发整条链路重建，放大了中断。此次消除该额外依赖，没有修改 monitor 的保护和恢复状态机。

新探针使用经证书校验的 `https://1.1.1.1/cdn-cgi/trace`，备用为 `https://1.0.0.1/cdn-cgi/trace`。入口认证探针与命名空间出口探针使用相同端点集合、解析方式和预期日本 IP。每次必须获取新鲜 HTTP 200，并验证唯一、合法的 `ip=`。

备用尝试共享原有 12 秒总期限；只允许传输失败、超时、429 或 5xx 尝试下一端点。TLS 失败、身份不符、重定向、其他 4xx、格式异常和过大响应立即失败。所有端点失败仍进入保护；没有缓存成功、延长健康宽限期或绕过隧道。两端点同属 Cloudflare，只提供端点冗余，不能视为跨供应商容灾。具体决策见 [ADR 006](../../adr/006-bounded-egress-probe-redundancy.md)。

OpenVPN TCP 两端增加 `socket-flags TCP_NODELAY`，认证探针中继的两端 socket 也关闭 Nagle。VPN-over-proxy 顺序、服务器端承载秘密、国内直连规则、受保护流量 fail-closed 均保留。未引入多路复用、改换协议或绕过 VPN。

## 延迟与速度

延迟用同一 Cloudflare 小响应测量；新连接每次独立 curl，复用连接排除首个新建样本。下载每条路径 3 次 2 MiB；上传每条路径 2 次 2 MiB，日本另做两路并行各 1 MiB 的短时测试。测试请求经 TLS 验证；上传为合成测试数据。它们是有限样本，不是持续容量或 SLA。

| 测量 | 修复前 | 修复后 | 解释 |
| --- | ---: | ---: | --- |
| 日本直接新建 HTTPS 中位数 | 64.9 ms | 64.2 ms | 日本至目标基线基本不变 |
| 阿里云经现有完整业务链路新建 HTTPS 中位数 | 259.2 ms | 170.7 ms | 发送参数调整后有改善迹象，未做反向 A/B 隔离因果 |
| 手机新建 HTTPS 中位数 | 604.6 ms（LTE） | 493.0 ms（Wi-Fi） | 网络条件改变，不能把差值全归因于补丁 |
| 手机复用连接首字节中位数 | 85.6 ms（LTE） | 70.4 ms（Wi-Fi） | 接近现有路径往返量级 |
| 手机复用连接小响应完成中位数 | 120.3 ms（LTE） | 70.5 ms（Wi-Fi） | 仅本次目标和样本 |
| 日本公网直接下载中位数 | 8.906 Mbps | 9.028 Mbps | 入站明显高于出站 |
| 阿里云完整业务链路下载中位数 | 约 1.65 Mbps | 1.640 Mbps | 吞吐基本未改善 |
| 手机核心代理下载中位数 | 1.360 Mbps（LTE） | 1.575 Mbps（Wi-Fi） | 手机浏览器前轮另测 1.678 Mbps |

手机新连接从发起到目标 TLS 完成累计中位数约 424 ms；此计时包含本地代理请求、代理建连、DNS、远端 TCP 和目标 TLS，不能说全部是 TLS 加密耗时。复用请求约 70 ms 说明每次新建连接的准备过程占较大部分。用户手动停止后，进一步拆解 CONNECT 与 TLS 的测试连接被拒绝，故尚不能精确分配到每一子阶段。

旧样本还测得手机至阿里云 ICMP 平均 51.2 ms、阿里云至日本承载 TCP 建连平均 41.7 ms、VPN 对端 RTT 平均 46.6 ms、日本至 Cloudflare ICMP 平均 3.2 ms。这些使用不同协议和路径，不能简单相加当作手机 HTTPS 时延。

日本直接上传两次为 1.852 / 1.872 Mbps，两路并行上传总吞吐仍约 1.848 Mbps，支持“日本出站存在约 2 Mbps 的共享瓶颈”，尚不能仅凭测量证明购买套餐限速。阿里云直接上传约 3.13 / 3.27 Mbps，也可能成为日本扩容后的下一约束。

下载时日本承载 TCP 的最小 RTT 42.273 ms、当时平滑 RTT 153.456 ms，说明负载时有额外排队或路径波动；它可以解释满载时增加的约百毫秒，不能独自解释空闲新连接的全部耗时。TCP 也观察到乱序指标，但没有证明大量丢包重传是当前吞吐主因；没有明显 CPU 饱和证据。见 [负载期 TCP 摘要](loaded-tcp.json)。

本轮手机国外出口仍验证为日本。国内镜像返回 HTTP 403，错误页未计为下载速度；新的路由日志未取得，不能声称重做完整国内分流验收。此前 LTE 国内直连证据仍见[原手机测试](../android-routing-speed-2026-10-20/README.md)。本轮没有完成所有应用 TUN、DNS/IPv6/UDP 矩阵或 Wi-Fi/蜂窝切换验收。

## 套餐调查与后续方向

已查看[衡天云日本产品页](https://www.htstack.com/jp-cloud.shtml)：公开页面存在 2 Mbps 与 5 Mbps 档位。浏览器控制台跳转登录，没有当前账户会话，因此无法核实用户旧“日本标准版 S4”的实际购买带宽、合同或费用。公开价格表不是这台实例套餐的证明，未登录账户、购买或变更套餐。

当前证据支持优先确认并提高日本公网出站额度来提升吞吐；它不会自动消除首次建连耗时。延迟后续应在相同手机网络、客户端运行时补齐 CONNECT、DNS、目标 TLS 分段，再评估连接复用；任何多路复用或协议调整还需保持 VPN-over-proxy 和 fail-closed，不能直接把未经验证的参数投入生产。
