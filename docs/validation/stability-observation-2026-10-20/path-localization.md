# 日本侧与跨境路径定位（2026-10-21 UTC）

**优先怀疑日本实例所在的虚拟网络、机房网关或公网接入路径；尚未锁定具体设备。** 08:27/08:28 的历史事件同时影响日本宿主直连外部目标和中日连接，“只有跨境线路故障”不能完整解释现象。客体 CPU、内存、网卡和应用进程故障目前缺少直接证据，但不能仅凭客体内的正常计数器排除宿主机或虚拟网络问题。

这不是根因修复结论。新增约 10 分钟对照没有重现共同断连，原定 24 小时观察仍进行中。

## 路径核实

日本宿主查询 `1.1.1.1`、`8.8.8.8` 和阿里云公网地址，均从物理虚拟网卡 `ens17` 经机房网关 `10.1.251.1` 发出；默认路由与标准 local/main/default 策略表没有指向阿里云或业务 VPN。客体为 KVM、virtio_net，MTU 1450。现有 HTTP 对照显式禁用环境代理和 curlrc。

日本两个 HTTPS 对照在本次复核均返回 HTTP 200、TLS 校验成功、出口 IP 匹配，Cloudflare 自报机房码为 NRT。日本到 Cloudflare/Google DNS 的 ICMP 中位约 3 ms，明显区别于到阿里云约 39 ms。由路由与这些测量共同支持：日本外部对照不依赖 Wayvia 的中日承载连接。当前测量不能证明历史每个数据包的逐跳路径相同。

## 有限对照结果

通过既有 SSH 启动[独立只读脚本](observe_path_localization.py)，两端各 120 轮、间隔 5 秒，约 595 秒后因 `cycles_complete` 正常退出。入口 08:42:12–08:52:07，日本 08:42:13–08:52:08。仅发送固定目标的低频 ICMP 与 TCP 建连；没有认证尝试、业务正文、抓包或配置写入。它没有安装持久服务，也没有替换或重启原 24 小时采样器。

| 对照 | 入口成功数 / 中位耗时 | 日本成功数 / 中位耗时 |
| --- | --- | --- |
| 本机默认网关 ICMP | 120/120，0.073 ms | 120/120，0.088 ms |
| 跨境对端 ICMP | 120/120，38.6 ms | 120/120，38.6 ms |
| 跨境 SSH TCP 建连 | 120/120，41.85 ms | 120/120，42.27 ms |
| 跨境代理监听 TCP 建连 | 120/120，42.25 ms | 120/120，43.43 ms |
| 本机代理监听 TCP 建连 | 120/120，0.29 ms | 120/120，0.28 ms |
| Cloudflare ICMP | 113/120，成功时 217 ms | 120/120，3.04 ms |
| Google DNS 地址 ICMP | 120/120，38.0 ms | 120/120，2.86 ms |

TCP 端口能建立连接不等于代理认证和完整业务路径通过，需与原生产 monitor 一起判断。新增的入口直连 Cloudflare ICMP 七次无响应是单独的路径对照，不能计为代理断连；它也不是原有宿主 HTTPS 超时基线的同一种测量。

两端新增窗口内网卡 errors/dropped 与 softnet dropped 均无增长。只读快照显示日本 qdisc drops/overlimits/backlog 为 0，连接跟踪约 198/8192，virtio 驱动错误计数为 0。日本现有防火墙允许阿里云访问 443，额外丢弃计数属于其余来源的 443 入站限制；该规则不解释日本对外 ICMP/DNS 同时失败。以上是当前配置/计数器证据，不是历史故障时的逐包记录。

低频 MTR 中，日本到 Cloudflare 终点三次回复约 3.07 ms，阿里云到日本终点三次约 40.41 ms。中间跳不回应或 RTT 高于终点不能单独判定该跳故障；日本到阿里云的本次 MTR 没有可用跳表，保留为测量限制。

## 能区分到哪一层

| 候选位置 | 当前证据 | 当前判断 |
| --- | --- | --- |
| 日本客体内应用、CPU 或内存 | 故障先于保护重建；未见持续资源耗尽、OOM、网卡错误 | 缺少支持，不能完全排除未采到的短暂问题 |
| 日本虚拟网络、机房网关、公网映射或共同上游 | 日本对多个外部目标与跨境连接同时异常；这些路径在日本侧共享接入边界 | 优先核查，但尚不能指定 NAT、交换机或某条上联 |
| 仅中日跨境路径 | 跨境确有双向无响应和 TCP 重传，但日本直连外部 HTTP/DNS 同时异常 | 单独这一原因不足以解释全部现象；不排除同一上游事件同时影响多条路径 |
| Wayvia 保护逻辑是最初原因 | 首批网络和请求错误早于服务停止/恢复 | 不支持；保护后的额外中断须与最初故障分开 |

关键缺口是：08:27/08:28 时没有日本网关和 loopback 端口的同步样本。本轮补充采样已经结束，不能拿事后的 120/120 成功倒推出历史正常，更不能宣称已确认供应商故障。仅靠客体 SSH 无法取得物理宿主、虚拟交换机或供应商公网映射设备的历史计数器。

后续优先取得这两个事件窗口的宿主机、虚拟交换网络、网关及上联记录，或在下一次自然异常时取得网关/本机同步证据。已准备[供应商核查材料草稿](provider-network-investigation-draft.md)，**未向任何人发送**。继续保留真实超时根因未解决，不修改生产阈值，不做故障、重启或迁移测试。
