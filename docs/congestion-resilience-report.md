# Wayvia 拥塞断线问题：原因、改动与验证报告

日期：2026-11-02。分支：`codex/congestion-resilience`（基于生产运行版本 `0873d61`）。状态：仓库实现与隔离实验完成，**未部署到生产**。

本文面向汇报与评审，按"现象 → 证据 → 源码原因 → 原设计考虑 → 新方案 → 验证数据 → 代价与边界 → 常见问题"组织。所有数字都标注来源；原始证据见文末索引。

## 1. 一句话结论

日本出口只有 2 Mbps 出站带宽。设备一旦把它跑满（无论上传还是下载），隧道内排队数秒，健康检查超时；原有监控"一次检查失败就停入口、下一轮整链重建"，把"变慢"放大成"所有设备断线"。改动后：满载时检查耗时从约 3–6 秒（多数超时）降到 0.015–0.18 秒且零失败；带载变慢不再触发断线；真正的故障仍立即保护；不会出现直连泄漏。代价是整形后吞吐下降 14–19%。

## 2. 用户可感知的现象

- 晚间经常整体断线几秒到几分钟，所有设备同时受影响。
- GitHub、ChatGPT "又慢又不稳定"。核查发现二者本来就走日本代理，日志里它们的失败全部落在整链重建的时刻——是整条链路在断，不是这两个网站或分流规则的问题。

## 3. 生产证据（只读核查，2026-11-02）

来源：[问题范围记录](validation/congestion-scope-2026-11-02/README.md)。时间为北京时间。

| 10-20 至 11-02 降级记录 | 122 | 49 |

### 3.3 典型一晚：11-01 21:42–23:31

- 入口整链重建 **10 次**，日本同期一直健康（它自己的检查都正常）。
- 21:42–21:54：设备 JXY 下载 0.8–1.45 Mbps，触发 4 次。
- 22:22–23:36：JXY **持续上传约 2 Mbps**（下载近零），触发其后 6 次；流量回落到近零的 22:40–22:47、23:20–23:26 没有失败。
- 同期入口日志：`api.github.com`、`alive.github.com`、`chatgpt.com` 连接在 5 秒左右 `i/o timeout`，时间点与重建一致。

### 3.4 带宽与缓冲

- 日本实例配置 2 Mbps（10-21 供应商控制台核实）；实测下载约 9 Mbps、上传约 1.86 Mbps，即**限速在日本出站方向**。
- 关键推论：设备**下载**的数据要从日本经隧道发回阿里云，设备**上传**的数据要从日本发往目标网站，**两者共用日本这 2 Mbps 出站**。所以单台设备上传也会拖垮所有人的下载和检查。
- 日本承载连接（sing-box，端口 443）的发送缓冲实测已自动增长到 **2.2 MiB**，按 2 Mbps 算约 **9 秒**积压；两端网卡 `fq_codel` 队列为 0，说明排队不在网卡，而在 TCP 缓冲和供应商限速器里。

### 3.5 不能用带宽解释的部分

7 个事件（约三分之一）发生在零流量。其中 10-27 10:48、11:43 两次是阿里云和日本**同时**失败、重建多次验证失败，属于日本上游或跨境网络事件；其余几次当时没有隧道时序数据，无法定位。**本次改动解决的是拥塞放大断线；零流量那部分要靠后续的分层恢复和观测补强。**

### 3.6 日志与观测现状

- monitor 每 15 秒把完整状态 JSON 写入 journal：实测每轮 6.8 KB，加上每轮约 1.2 条事件（每条约 0.8 KB），合计约 **44.9 MB/天/台**。
- 日本 OpenVPN 约 13.5 万行/天，主要是检查本身的建连/复位，真实事件被淹没。
- journald 占用：阿里云 904 MB、日本 1.3 GB；日本主机 1 GiB 内存，journald 常驻 162 MiB。
- sing-box 只记 `warn`，看不到正常连接的目标与字节；隧道 RTT/重传/队列没有连续记录——这正是零流量事件无法定位的原因。

## 4. 源代码层面的原因

### 4.1 判定：一次失败即保护，下一轮整链重建

`src/wayvia/agent/transactions.py` 原 `monitor()`：

```python
healthy = self._observe(tx, plan)      # 七层检查，任一层失败即 False
if not healthy:
    tx["state"] = State.DEGRADED        # 一次失败就降级
...
if tx["state"] == State.DEGRADED:
    self._protect(plan, tx)            # protect() = systemctl stop wayvia-ingress
```

下一轮（`wayvia-monitor.timer`，`OnUnitActiveSec=15`）进入 `elif tx["state"] == State.DEGRADED: self._rebuild(tx)`，`_rebuild()` 重放整个计划：namespace → guard → 配置 → veth → NAT → 依次重启 carrier、VPN、bridge、ingress 全部服务。

- 检查期限：HTTP 检查单次尝试约 5.75 秒（`Probe.timeout` 默认 5 秒，主备两次尝试）。拥塞时隧道内排队 3–9 秒，必然超时。
- 失败原因不区分：超时、TLS 中断与"证书不对""会话断了"走同一条路径。
- 重建没有频率限制：恢复后又拥塞，就再停、再重建（11-01 一晚 10 次）。

### 4.2 网络：所有流量挤在一条 TCP 里

链路是"设备 → 阿里云入口 → OpenVPN（TCP）→ Trojan/TLS（TCP）→ 日本"。所有设备、所有连接和检查本身，都封装在**同一条**跨境 TCP 承载连接里：

- 队头阻塞：检查的 TLS 握手包必须排在已写入承载的大量下载/上传数据后面。
- 网卡公平队列（`fq_codel`）只看到一条流，无法让检查插队。
- Linux 默认 `tcp_wmem` 上限 4 MiB、`tcp_notsent_lowat` 不限，承载套接字可以囤积数秒数据（实测 2.2 MiB）。

### 4.3 日志：每轮全量、每条一个事务

- `src/wayvia/agent/recovery.py` 每轮 `print(json.dumps(result))` 输出完整状态（含每层所有尝试细节和上下文字段）；`transactions._event()` 每轮写一条 `health_healthy`。
- 诊断采集器 `telemetry/collector.py` 每 5 秒一轮，每条记录调用一次 `store.append()`；每次都开一个 `BEGIN IMMEDIATE` 事务、强制同步提交（`synchronous=FULL`），先做一次清理 DELETE，再对 incidents×records 做一次全量 pin 关联——一轮约 11–13 个事务。
- 日志库清理是一条不限行数的 DELETE，过期数据多时长时间持锁。

## 5. 为什么原代码这样写

这不是疏忽，而是早期设计在"安全优先、行为可证明"下的合理选择：

1. **fail-closed 是第一原则**（[ADR 002](adr/002-privileged-network-transactions.md)）：受保护流量绝不能在代理/VPN 故障时直连泄漏。健康状态不确定时选最保守的动作——停入口——不需要证明"现在安全"。
2. **整链重建最简单、最可验证**：按固定顺序重放整个计划，保证 guard 先于服务、凭据用最新版本，不需要判断"到底哪个组件坏了"。分层恢复要先回答"保护是否依赖停入口"，在没有隔离负向实验前，[恢复决策表](recovery-decision-table.md)第 3 条明确禁止放宽阈值或加宽限。
3. **设计时没有"负载"的概念**：检查被设计成"路径通不通"，默认失败就是故障。2 Mbps 的出站额度到 10-21 才在控制台核实，那之前的观察窗口把超时当作网络故障排查。
4. **TCP 承载是架构约束**：VPN-over-proxy 顺序（OpenVPN 走在 Trojan 代理之上）是设计要求（ADR 001），承载天然是 TCP；队头阻塞是这一结构在小带宽下的固有代价。
5. **日志先求完整**：故障排查阶段需要每轮全量证据；每条一个事务、强同步提交是为了证据"不丢、可审计"。当时没有对 1 GiB 内存主机上的长期体积做预算。

## 6. 新方案

全部改动在 `codex/congestion-resilience`，设计决定见 [ADR 014](adr/014-congestion-aware-health-and-exit-shaping.md)（修订 ADR 002）。

### 6.1 健康判定：区分"忙"和"坏"（升级后自动生效）

- **失败分类**（`TransactionManager.soft_errors`）：只有传输/期限类错误可能是负载——`HTTP_TIMEOUT`、`HTTP_DEADLINE`、`HTTP_TRANSPORT_FAILED`、`HTTP_TLS_TRANSPORT_FAILED`、`COMMAND_TIMEOUT`、`PROBE_DEADLINE`、`VPN_IDENTITY_TIMEOUT`。其他一律立即保护：证书/身份不符（`HTTP_TLS_FAILED`、`HTTP_IDENTITY_MISMATCH`、`VPN_IDENTITY_REJECTED`）、VPN 会话断开、guard 缺失、服务不活跃、探针异常、没有错误码的失败。一轮中只要有一层是"硬故障"，整轮按立即保护处理。
- VPN 身份检查原来只返回成功/失败，现在区分超时、拒绝与其他失败（`probe_runtime.vpn_identity`），否则带载变慢和证书错误无法区分。
- **承载进展信号**（`LinuxExecutor.carrier_counters()`）：用 `ss -tin` 读承载 TCP 的 `bytes_received`。同一连接两次采样之间收到的字节在增加 = 对端仍在收到本端 ACK，路径在前进；OpenVPN 每 10 秒的 keepalive 保证空闲时也有流量。读不到（域名承载、套接字变了）按"未知"处理。生产承载配置为数字 IP（非域名），可识别。
- **连续确认**：软失败时，无进展/未知连续 3 轮（约 45–60 秒）才保护；承载仍在前进视为"带载变慢"，连续 20 轮（约 5 分钟）仍失败才保护。期间状态保持 ACTIVE，但证据记失败，**配置发布仍被阻止**（`services/diagnostics.py` 要求全部证据健康）。
- **重建退避**：1 小时窗口内第 1–6 次重建距上一次至少 0/30/60/120/240/300 秒，之后都按 300 秒；等待时保持保护，状态里给出 `rebuild_after`。开机恢复不受限制。

数字的取舍：3 轮 ≈ 45–60 秒，覆盖生产中观测到的单次拥塞尖峰（多为 10–20 秒），真正断网时比原来晚约 30 秒发现；20 轮 ≈ 5 分钟，是"大文件长时间跑满"仍判为正常使用的上限，超过则仍保护，避免无限宽限。退避上限 300 秒避免一小时内反复整链重启。

### 6.2 日本出口整形（默认关闭，可选启用）

固定事务动作 `shaping`（`agent/models.py` `ShapingSpec`，`adapters/linux` `_shape`），随计划应用、确认、回滚：

1. **网卡 HTB**：日本物理出口总速率限在额度约九成（推荐 1800 kbit），使供应商 FIFO 始终不积压；承载流（日本 443 出站）保证份额（推荐 1600 kbit），其他出站（设备上传到目标）用剩余份额，两类都可借用到总速率，叶子 `fq_codel`。
2. **隧道公平队列**（`tunnel_kbit`，推荐 1450 kbit）：在日本 VPN `tun0` 上 HTB + `fq_codel`。tun0 上每条内层连接可区分，积压留在这里，检查和网页请求不再排在大下载后面。**必须低于承载保证份额并留约 8% 封装开销**，否则上传竞争时积压回到承载套接字（实验反例 P95 约 2 秒）；配置模型强制 `tunnel_kbit < carrier_kbit`。
3. **`tcp_notsent_lowat`**（默认 131072）：限制套接字未发送积压。
4. **自愈**：OpenVPN 重启会重建 tun0 并丢掉队列。monitor 每轮调用 `ensure_shaping()`，按 Wayvia 状态文件补回（事件 `shaping_restored`），失败不影响健康判定。
5. **安全**：接口上已有非 Wayvia 的自定义根队列时拒绝启用；关闭时只删 Wayvia 自己的；回滚恢复原队列和原 sysctl。

**阿里云不整形**：该主机还运行另一套生产应用（miaoban：API、worker、PostgreSQL），网卡和主机级 TCP 参数是共用的。

### 6.3 日志降噪与写入成本

- monitor 健康且各层 ≤2 秒的轮次只输出每层状态与耗时；失败、变慢、软失败、非 ACTIVE 输出完整证据。`health_healthy` 改为状态变化或每 5 分钟心跳，`health_congested`/`health_degraded` 每轮输出。
- 诊断采集器每轮批量写入（`DiagnosticStore.append_many`）：一个事务、一次清理、一次 pin 关联，检查点同事务提交（崩溃时不会出现"检查点前进了但数据没存"）。每轮约 11–13 个事务降到 2 个。
- 日志库清理每批最多 1000 行，显式清理循环分批提交。查询本身按保留期过滤，分批删除不会让过期数据被查到。
- 可选 journald 上限 `deploy/journald/wayvia-limits.conf`（1 GiB/30 天）。它是主机级设置，阿里云共用主机需业主同意，不自动安装。

### 6.4 分流

`policy.proxy_domains`（默认空）把指定域名固定走代理和代理 DNS，排在国内域名/IP 规则之前。建议填 `chatgpt.com`、`openai.com`、`oaistatic.com`、`oaiusercontent.com`：国内直连实测 3 次全部超时，日本直连正常。GitHub 保持现状：它本来就经日本，慢是因为整条链路被拥塞拖垮。

## 7. 验证数据

### 7.1 隔离实验：共享 2 Mbps 出站

来源：[实验记录](validation/congestion-lab-2026-11-02/README.md)、[结构化结果](validation/congestion-lab-2026-11-02/congestion-result-256kb.json)。

方法：一次性 Linux 容器（`--network none`，内核 6.8），复用正式渲染配置与锁定组件（sing-box 1.14.3、OpenVPN 2.6.19、v2rayA 2.5.10）。日本只有一个上联，经"供应商桥"用 2 Mbit FIFO（256 KB 缓冲）限制日本发出的所有流量——与生产"上传和下载共用日本出站"一致。设备用 4 条 TCP 上传、下载或双向满载 60 秒；每秒发一次检查（5.75 秒期限）。整形全部走生产代码。

**检查耗时（egress 层，p50 / p95）与失败数**

| 场景 | 优化前 | 仅网卡整形 | 推荐参数（网卡 + 隧道公平队列） |
| --- | --- | --- | --- |
| 空闲 | 0.008 / 0.019 s，0/59 | – | 0.008 / 0.019 s，0/59 |
| 上传满载 | 3.219 / 3.847 s；6/8 超过 3 秒 | 0.028 / 0.128 s，0/53 | **0.015 / 0.055 s，0/55** |
| 下载满载 | 5.896 / 5.947 s；**5/6 超时** | 5.882 / 5.942 s；5/6 超时 | **0.030 / 0.055 s，0/54** |
| 双向满载 | 5.881 / 5.946 s；**5/6 超时** | 5.877 / 5.921 s；5/6 超时 | **0.115 / 0.183 s，0/44** |

设备端完整路径检查结论相同（推荐参数 p95：上传 0.050、下载 0.051、双向 0.212 秒）。优化前每秒一次的检查在 60 秒里只完成 6–8 次，因为每次都要等 3–6 秒。

**吞吐（Mbit/s）**

| 场景 | 优化前 | 仅网卡整形 | 推荐参数 |
| --- | ---: | ---: | ---: |
| 上传满载 | 1.773 | 1.520 | 1.517（−14%） |
| 下载满载 | 1.699 | 1.557 | 1.380（−19%） |
| 双向：上传 / 下载 | 0.277 / 1.354 | 0.107 / 1.422 | 0.169 / 1.355 |

**积压位置（满载中段快照）**

| 场景 | 积压在哪 | 大小 |
| --- | --- | --- |
| 上传，无整形 | 供应商 FIFO | 约 160 KB |
| 下载，无整形 | 日本承载套接字未发送队列 | 约 615 KB（约 4 秒） |
| 下载，仅网卡整形 | 同上 | 约 184 KB |
| 推荐参数 | tun0 `fq_codel`（按流公平） | 数 KB |

**排除的方案**（30 秒探索）：`tcp_notsent_lowat` 降到 16 KB、OpenVPN `sndbuf/rcvbuf 64 KB` 与 `tcp-queue-limit 16`，单独或组合，下载满载时检查 p50 仍为 4.6–5.8 秒。

**其他实验结论**

- 所有满载场景中，入口与出口承载连接每 15 秒的 `bytes_received` 都在增加——"承载仍在前进"信号在拥塞时稳定成立，所以新判定不会把带载变慢误判为故障。
- OpenVPN 重启后 tun0 队列回到默认 `fq_codel`；`ensure_shaping()` 恢复 `htb`，再次调用为空操作。
- **宽限期安全**：入口和终端保持运行、上传满载中，分别杀掉日本 OpenVPN 与日本代理：受保护流量与原生流量均失败（不直连），国内直连与管理回程正常；目标服务器全程只看到日本 NAT 地址 `10.74.0.1`。

### 7.3 用新规则回看生产事件（估算）

对 10-26 18:35 部署后的 21 个入口事件，按失败类型归类：

| 类别 | 事件数 | 新规则下 |
| --- | ---: | --- |
| 全部为超时/传输类，且只降级一轮 | 10 | 不会保护（需连续 3 轮） |
| 超时/传输类，持续 2–4 轮 | 5 | 只 2 轮的不保护；3–4 轮的取决于承载是否仍在前进 |
| 含承载检查失败，但旧版本没有错误码 | 5 | 新版本区分超时（软）与拒绝（硬），历史数据无法判断 |
| 含 VPN 会话失败（硬故障） | 1 | 仍立即保护 |

即至少约一半（10/21）的整链断线会被消除，上限约 20/21。11-01 晚 21:42–23:31 的 8 次降级，失败层全部是超时/传输类。这是按失败类型的估算：历史上没有记录承载进展，也无法知道"不重建时下一轮是否健康"，需上线后用同样口径复核。

## 8. 代价、风险与未完成

1. **吞吐代价**：上传 −14%、下载 −19%，高于方案的 ≤10% 目标；双向同时满载时上传只剩约 0.17 Mbit/s（隧道方向优先）。根本原因是额度只有 2 Mbps，整形必须留余量。可在生产实测额度与突发后上调参数，或扩带宽。
2. **真故障发现变慢**：超时类故障从约 15–30 秒变为 45–60 秒（承载仍在前进时最长约 5 分钟）。硬故障不变。
3. **实验与生产差异**：供应商限速器的缓冲大小与突发是假设（256 KB FIFO）；实验在 arm64，生产为 x86_64；没有运行真实 monitor 计时器。
4. **正式事务实验未完成（环境阻塞）**：第一次运行被 10-12 遗留的实验网络挡住（已用 `make clean-lab` 按标签清理）；第二次在出口"应用并确认"时 CLI 报 `OSError`。在保留的容器内复现得到 `OSError: [Errno 28] No space left on device`——开发机 Docker 虚拟机 59 GB 磁盘已满，主要被其他项目的卷和镜像占用；改动前的提交 `0873d61` 在同一环境下同样在安装阶段因磁盘写入失败。该阶段覆盖正式安装、计划/确认、回滚与恢复，**释放磁盘并通过之前不应部署**。
5. **零流量故障**（约三分之一）不在本次范围：需要分层恢复（待办 12）和持续诊断采集器上线。
6. **OpenVPN 检查日志噪声**未处理：该检查有价值，降噪需另行实验。

## 9. 上线建议

1. 先解决 8.4，再在生产升级软件（判定、退避、日志降噪随升级生效，不改网络）。
2. 观察 3–7 天：`health_congested` 次数、降级次数、`rebuild_after` 出现情况、journal 增速。
3. 用户确认吞吐代价后，在日本出口启用 `shaping`（推荐参数），核对 `tc -s qdisc show dev ens17`、`tc qdisc show dev tun0`；对照启用前后同时段的降级次数与设备流量。
4. 视情况配置 `policy.proxy_domains` 并重新发布订阅；评估 journald 上限（日本可装，阿里云需业主同意）。
5. 回滚：删除 `shaping` 配置重新发布即移除整形；软件回退按既有升级回退流程。

## 10. 汇报时可能被问到的问题

**为什么不直接把日本带宽升到 5–10 Mbps？**
这是最直接的缓解，建议同时评估（需付费，用户决定）。但扩容只是提高了"跑满"的门槛：任何一个大文件依然能跑满，原判定依然会整链断线。判定改动和整形在任何带宽下都需要；整形参数按新额度等比例调整即可。

**放宽判定会不会导致流量直连、泄漏？**
不会。宽限只推迟"停入口并重建"，不放开任何直连路径。防直连靠的是独立的 namespace guard 和 VPN-over-proxy 顺序，与入口是否停止无关。隔离实验在宽限期内分别杀掉 VPN 层和代理层，目标只看到日本地址，受保护流量全部失败而不是绕路。

**真的出故障了，会不会要等 5 分钟才发现？**
只有"承载连接仍在正常收发数据、但检查超时"这种情况才会最长宽限约 5 分钟——此时路径确实在工作，只是慢。承载停止前进时 3 轮（约 45–60 秒）就保护；证书/身份错误、会话断开、服务挂掉等仍立即保护。

**3 轮、20 轮、0–300 秒退避这些数字怎么来的？**
3 轮覆盖生产中常见的 10–20 秒拥塞尖峰，同时把真故障发现延迟控制在 1 分钟以内；20 轮约 5 分钟，是"长时间跑满属于正常使用"的上限；退避逐级翻倍、封顶 5 分钟，参考 11-01 一晚 10 次重建的情况。都是常量，可按生产观测调整。

**吞吐下降 14–19% 值得吗？**
优化前满载时检查 5/6 超时、所有设备反复断线；优化后零失败、网页请求 0.1 秒内响应。对家庭/小团队使用，稳定比峰值速度重要。整形默认关闭，由用户决定是否启用，也可上调参数换取吞吐。

**为什么不能只在网卡上整形？**
实验证明网卡整形只解决上传。下载时所有数据和检查回包在同一条承载 TCP 里排队（积压 184–615 KB），网卡看到的只有一条流。必须在 tun0（内层流可区分）上做公平队列。

**为什么 tun0 速率要低于承载份额？**
上传和下载同时满载时，承载流只能拿到保证份额；如果 tun0 放进来的数据比这多，多出的部分又会积压在承载套接字里。实验反例（tun0 1600、承载 1200）检查 p95 约 2 秒；推荐参数（1450 < 1600）为 0.18 秒。

**为什么不调 OpenVPN 缓冲或改 BBR/UDP？**
OpenVPN 缓冲和更小的 `notsent_lowat` 已在实验中排除。BBR 只改发送节奏，不能解决单流内的队头阻塞。UDP 承载与 VPN-over-proxy 的 Trojan TCP 架构冲突，属于架构变更，不在本次范围。

**阿里云为什么不做？**
阿里云主机上还跑着另一套生产应用，网卡和主机 TCP 参数共用，整形会影响它。瓶颈在日本出站，日本侧整形已覆盖上传和下载两个方向。

**另外三分之一零流量的断线怎么办？**
本次不解决。证据指向日本上游/跨境网络事件，但缺少隧道时序数据。下一步是上线已开发的持续诊断采集器（5 秒级 RTT/重传/队列，降级前后自动留存），再做分层恢复，减少每次保护的影响范围。

**日志减少了，排障会不会少信息？**
不会少关键信息：健康轮仍保留每层状态与耗时（监控告警需要的新鲜度数据），任何失败、变慢（>2 秒）、软失败和非健康状态都输出完整证据。减少的是重复的健康轮细节。

**GitHub 和 ChatGPT 要不要改走日本？**
它们本来就走日本。ChatGPT 建议用 `proxy_domains` 固定（国内直连完全不通）；GitHub 不建议改直连，否则离开受保护范围，而且校园直连同样不稳定，它慢的根源是拥塞。

**实验可信吗？**
用的是正式渲染配置和锁定版本的真实组件、生产代码路径；瓶颈模型抓住了"上传下载共用日本出站"这一关键结构。差异在供应商限速器细节和 CPU 架构，所以实验只证明机制有效，生产效果需要上线后用 7.x 同样的指标复核。

**怎么回滚？**
整形是事务动作，删除配置重新发布即恢复原队列和原 sysctl；判定逻辑随软件版本，按既有升级回退流程回到旧 wheel。
