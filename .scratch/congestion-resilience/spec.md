## 背景与证据

来源：[问题范围核查](../../docs/validation/congestion-scope-2026-11-02/README.md)。

- 10-20 至 11-02 阿里云入口 82 个降级事件（约 6 次/天），其中 65 个只降级一轮、下一轮重建即恢复；日本出口 30 个，10-27 后仅 3 个。
- 有负载历史的 21 个入口事件：业务 ≥0.5 Mbps 的分钟事件率约 2%，<0.1 Mbps 约 0.08%，相差约 25 倍。
- 11-01 全天入口整链重建 10 次，其中 21:42–23:31 晚间 8 次降级，失败层全部为超时/传输类：JXY 先下载 0.8–1.45 Mbps，22:22–23:36 持续上传约 2 Mbps。GitHub、ChatGPT 的失败全部落在重建时刻。
- 日本实例出站 2 Mbps（10-21 控制台核实；实测下载约 9、上传约 1.86 Mbps）。设备下载（日本 → 阿里云隧道）与设备上传（日本 → 目标）共用这份出站额度。日本承载套接字发送缓冲实测约 2.2 MiB（约 9 秒积压）。
- 约三分之一（7/21）事件发生在零负载，其中 10-27 两次两端同时失败，属日本上游/跨境网络事件。**整形只解决拥塞部分。**
- 阿里云主机另有一套生产 Docker 应用（miaoban）共用网卡、内存与磁盘；日本主机只运行 Wayvia。

## 问题拆解

1. **排队在供应商限速器里**：日本出站超过 2 Mbps 后积压在看不见、管不了的 FIFO；本机 `fq_codel` 无积压。
2. **所有业务挤在一条承载 TCP 里**：网卡只看到一条流；下载满载时积压在日本承载套接字的未发送队列（实验 184–615 KB），检查回包排在后面。
3. **判定过于敏感**：一轮任一检查失败即停入口、下一轮整链重建，把"慢"放大成全体断线。
4. **单设备大流量可占满共享额度**，且当前日志无法知道它在传什么。

## 各阶段：原计划与实际结果

### 阶段 0：运维决策（未做）

- 评估日本带宽升级（5–10 Mbps）；整形参数按新额度等比例上调。
- 可选：按 [ADR 013](../../docs/adr/013-private-traffic-metadata-and-admin.md) 只对管理员自有设备开启连接目标元数据（依赖 L2）。

### 阶段 1：流量整形（已实现、生产已启用）

**最终方案**（固定事务动作 `shaping`，配置段 `shaping`，默认关闭，只用于日本出口）：

| 组成 | 参数（推荐） | 作用 |
| --- | --- | --- |
| `ens17` HTB 总速率 | `egress_kbit: 1800` | 总出站低于额度约一成，供应商 FIFO 不再积压 |
| 承载类（端口 443 出站） | `carrier_kbit: 1600`，可借到 1800 | 设备下载与检查回包的保底份额 |
| 其他出站类 | 剩余 200，可借到 1800 | 设备上传到目标 |
| `tun0` HTB + `fq_codel` | `tunnel_kbit: 1450` | 积压留在内层流可区分的位置，检查不再排在大下载后面 |
| `tcp_notsent_lowat` | 131072 | 限制套接字未发送积压 |

与原计划相比的变化：

- **CAKE → HTB + `fq_codel`**：两者都可用；HTB 按类保证份额更直接、行为更可预测。
- **隧道公平队列从"可选、待评估"变为核心**：实验证明网卡整形只修复上传，下载满载时唯一有效的是 tun0 公平队列。约束：`tunnel_kbit` 必须低于 `carrier_kbit`（留约 8% 封装开销），否则上传竞争时积压回到承载套接字（反例 P95 约 2 秒）；配置模型强制该约束。
- **tun0 自愈**：OpenVPN 重启会重建 tun0 并丢掉队列，monitor 每轮按状态文件恢复（`shaping_restored`）。
- **缩小承载缓冲（原第 3 项）被否定**：OpenVPN `sndbuf/rcvbuf`、`tcp-queue-limit`、`tcp_notsent_lowat` 16 KB 均无改善；选项保留但不推荐。
- **阿里云侧（原第 4 项）不做**：与其他业务共用网卡和主机 TCP 参数；瓶颈在日本，日本侧整形已覆盖上下行。

### 阶段 2：拥塞与故障分开判定（已实现、已部署）

- **失败分类**：传输/期限类（`HTTP_TIMEOUT`、`HTTP_DEADLINE`、`HTTP_TRANSPORT_FAILED`、`HTTP_TLS_TRANSPORT_FAILED`、`COMMAND_TIMEOUT`、`PROBE_DEADLINE`、`VPN_IDENTITY_TIMEOUT`）可能是负载；证书/身份、会话、guard、服务、无错误码的失败立即保护。VPN 身份检查新增超时/拒绝/失败三种错误码。
- **承载进展**：`ss -tin` 读承载套接字 `bytes_received`；同一连接在增长即"忙但在走"。生产承载为数字 IP，可识别。
- **连续确认**：无进展或未知时 3 轮（约 45–60 秒）才保护；承载仍在前进时 20 轮（约 5 分钟）。期间配置发布仍被阻止。
- **重建退避（与原计划不同）**：原计划"两次重建间隔若干分钟、限制每小时次数"，首版实现为"1 小时内所有重建都退避"。正式事务实验发现它让后续故障恢复多等 30 秒：降级时入口已停，推迟重建只会延长断线。**最终规则：同一次降级中前两次重建立即执行，此后失败的重建按 30/60/120/240/300 秒退避，成功即清零。**
- 安全前提已验证：宽限期内分别终止 VPN 与代理层无物理直出（实验）。

### 阶段 3：按失败层恢复（未做）

按[待办 12](../wayvia-deployment-followup/issues/12-software-timeout-recovery.md) 只恢复确认失效的组件，减少每次保护的断线范围；对零负载事件尤其有价值。

### 阶段 4：分流微调（已实现、生产未配置）

- `policy.proxy_domains`：在本地规则之后、国内域名/IP 规则之前固定走代理和代理 DNS；sing-box 与 mihomo 都输出；为空时配置 revision 不变。
- 建议配置 `chatgpt.com`、`openai.com`、`oaistatic.com`、`oaiusercontent.com`（国内直连实测 3 次全超时）。配置后需重新发布订阅。
- GitHub 不改：本就经日本，慢的根源是拥塞。

## 验证结果

### 隔离实验（[记录](../../docs/validation/congestion-lab-2026-11-02/README.md)）

共享 2 Mbit 出站（ifb + 256 KB FIFO），真实组件，60 秒/场景，检查期限 5.75 秒：

| 满载场景 | 优化前 egress p50 / p95 | 推荐参数 p50 / p95 | 吞吐 前 → 后 |
| --- | --- | --- | --- |
| 上传 | 3.22 / 3.85 s | 0.015 / 0.055 s，0/55 失败 | 1.773 → 1.517 Mbit/s（−14%） |
| 下载 | 5.90 / 5.95 s，5/6 超时 | 0.030 / 0.055 s，0/54 失败 | 1.699 → 1.380 Mbit/s（−19%） |
| 双向 | 5.88 / 5.95 s，5/6 超时 | 0.115 / 0.183 s，0/44 失败 | 上传 0.277 → 0.169，下载 1.354 → 1.355 |

对照原验收门槛：

| 门槛 | 结果 |
| --- | --- |
| 满载检查 P95 < 1.5 秒 | **达成**（≤ 0.183 秒） |
| 零降级 | **达成**（零探针失败；承载进展信号全程为真） |
| 总吞吐下降 ≤ 10% | **未达成**（−14% / −19%）；用户 11-03 确认接受 |
| 既有负向测试不变、代理/VPN 失效无直出 | **达成**（宽限期负向实验 + `make test-lab`） |
